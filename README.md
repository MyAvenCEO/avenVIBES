# avenVIBES

`@myavenceo/aven-vibes`

**A vibe is a complete little app** — view, style, state and logic in one bundle — rendered into an isolated shadow root, or to a string at build time.

The interface is *data*, not markup. So it can be stored, versioned, diffed, sent over a wire, validated before it renders, or generated by a model.

```bash
bun add @myavenceo/aven-vibes
```

## The whole idea

```ts
import { VibeEngine } from '@myavenceo/aven-vibes'

const engine = new VibeEngine({ container: document.querySelector('#app')! })

await engine.mount({
  view:  { tag: 'button', class: 'btn', text: '{state.label}', $on: { click: { send: 'TICK' } } },
  style: { tokens: { accent: '#d2a24a' },
           components: { btn: { background: 'var(--accent)', borderRadius: '9999px' } } },
  state: { label: 'Clicked 0 times' }
})
```

No template compiler. No build step for the view. The bundle is a plain object and the engine renders it.

## Why it is shaped this way

**Isolated by construction.** Every vibe mounts into its own shadow root with its own adopted stylesheet. A vibe cannot leak styles into your page and your page cannot bleed into it — which is what makes it safe to render a component you did not write.

**The view is data.** JSON, not markup. It can live in a database, be diffed, travel over a wire, or come out of a model — and be *validated* before it renders. A string of markup can do none of those safely.

**Logic runs sandboxed.** A vibe's behaviour executes in QuickJS compiled to WebAssembly, not on your main thread with your globals. It sees the state you hand it and nothing else.

**Renders to DOM or to string.** The same bundle renders into a live shadow root, or to HTML text at build time — so a static site keeps its content in the file, where search engines and readers without JavaScript can find it.

## What it is not

- **Not a React replacement.** It renders self-contained units *inside* an app, not the app itself. Routing, data loading and page structure stay with your framework.
- **Not a template language.** There is no expression compiler; a view resolves values through an evaluator you supply.
- **Not batteries-included styling.** It ships no design system. Tokens arrive through the bundle.

## API

The whole surface is a class, a function and a few types.

```ts
const engine = new VibeEngine({ container, containerName, onEvent })
await engine.mount(bundle)
await engine.updateState(partial)     // merges
await engine.replaceState(next)       // replaces
engine.getState()
await engine.unmount()

// Build-time rendering
const html = await renderViewToString(view, state, { evaluate })
```

### View nodes

| key | meaning |
| --- | --- |
| `tag` | whitelisted element name; anything unsafe becomes a `div` |
| `text` / `value` | resolved through your evaluator |
| `format: 'md'` | renders markdown, sanitised |
| `$each` | repeat a template over a list |
| `$slot` | pull in a named view from the registry |
| `$on` | dispatch an event; `$value` in a payload reads the input |

## Security posture

The point of data-as-UI is that the data might not be yours, so:

- Tags are whitelisted — anything else renders as a `div` rather than executing.
- Attribute values pass a whitelist that **strips quotes**, so a value cannot close its attribute and open a handler.
- Raw CSS is rejected outright; a style is structured data, never a string of CSS.
- URL attributes are scheme-checked. `javascript:` never survives.
- Markdown is sanitised through DOMPurify before it reaches the DOM.

## This site is built with it

The documentation site under `site/` is rendered by `renderViewToString` from view definitions — no hand-written HTML. That is partly a demonstration and mostly a test: if the renderer cannot carry a real multi-page site, it fails there before anyone builds a product on it.

```bash
bun run site
```
